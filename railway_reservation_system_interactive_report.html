Slide 01 • Executive Summary

Railway Reservation System (RRS)

High-Throughput Relational Architecture for Nationwide Multi-Stop Rail Networks

The Railway Reservation System (RRS) is an enterprise OLTP and analytics environment engineered for high-concurrency booking spikes, intermediate segment inventory reuse, and sub-150ms query response times.

It eliminates the intermediate segment dilemma through a Bitmask Segment Engine, enforces ACID consistency through two-phase distributed locking, and removes all anomalies across 3NF and BCNF normalization.

Key Architectural Pillars:

  • Bitwise segment reservation instead of whole-route seat blocking
  • Pessimistic row locking on target station legs during Tatkal rushes
  • Monthly range partitioning on journey_date for rapid partition pruning

Slide 02 • Core Problem

The Intermediate Segment Dilemma

Why static seat reservation models lose up to 65% of physical capacity

Traditional Naive Model: Single Static Booking

In naive models, a booking record is stored as Ticket(Train_ID, Seat_No, Date).

If a train travels NDLS ➔ KOTA ➔ BRC ➔ BCT, and Passenger A books Seat 12 from NDLS to KOTA, the seat is marked occupied for the entire route. When Passenger B requests KOTA to BCT, the system incorrectly reports zero vacancy.

Impact: Severe artificial capacity loss across multi-stop journeys.

Segment-Based Bitmask Engine

A route with $N$ halts yields $N - 1$ distinct sequential travel legs. Each physical berth maintains an occupancy bitmask:

NDLS ➔ KOTA (Leg 1): [1, 0, 0]
KOTA ➔ BCT (Legs 2 & 3): [0, 1, 1]
Bitwise Collision: (1 0 0 & 0 1 1) == 0 ➔ REUSABLE
Impact: Seat utilization increases from ~60% to over 96%.

Slide 06 • Relational Normalization

Formal Normalization (1NF ➔ BCNF)

Systematic elimination of redundancy and update/delete anomalies

1NF: Atomic Attributes

1NF

Violation: Storing passenger names as CSV string arrays: Ticket(pnr_no, passenger_names="Alice, Bob").

Resolution: Extracted into distinct Passengers entity where each tuple represents exactly one human passenger.

2NF: No Partial Dependencies

2NF

Violation: In Ticket_Passengers(pnr_no, passenger_name, train_name), train_name depends solely on pnr_no, not on the passenger.

Resolution: Split into Tickets(pnr_no, train_no) and Passengers(passenger_id, pnr_no, full_name).

3NF: No Transitive Keys

3NF

Violation: In Tickets(pnr_no, src_station, station_state), pnr_no determines src_station, which determines station_state.

Resolution: Removed station_state from Tickets. State is stored strictly inside Stations(station_code, state).

BCNF: Superkey Determinants

BCNF

Requirement: For every functional dependency $X \rightarrow Y$, $X$ must be a superkey.

Resolution: In Train_Schedules, enforce candidate keys via UNIQUE(train_no, stop_order) and UNIQUE(train_no, station_code).

Slide 07 • Concurrency Control

Tatkal Rush & Two-Phase Distributed Locking

Eliminating double-booking during peak morning reservation surges

Step 1 (0ms - 5ms)
Redis Redlock Token

Atomic key acquisition: SET lock:berth:12 token NX PX 480000. Fast-fails excess requests.

Step 2 (5ms - 25ms)
ACID DB Row Hold

Primary DB issues SELECT ... FOR UPDATE on Segment_Inventory to mark status LOCKED.

Step 3 (30s - 120s)
Payment Webhook

User completes UPI payment. On success, status transitions to CONFIRMED and PNR is issued.

Step 4 (Timeout / 8m)
Auto-Reclamation

If payment is abandoned, Redis TTL expires and an async worker resets the row to AVAILABLE.

Lock berth with temporary 8-minute reservation token UPDATE Segment_Inventory SET status = 'LOCKED', current_pnr = 'PNR8910421' WHERE inventory_id = 458021; -- 3.
